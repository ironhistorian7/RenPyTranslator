# 외부 문맥과 진단 로그

원문 Character 정의·따옴표 화자·화면 버튼·메뉴 근거로 확인된 이름표와 UI 라벨은 별도 요청으로 묶습니다. 이 요청에는 이야기의 공통·파일·장면 설명, 주변 대사, 관계 상태를 넣지 않고 해당 용어의 원문/한국어 표기와 변수·인명 정보를 전달합니다. HY와 일반 Chat/Instruct 모델 모두 항목 용도를 받습니다. 짧은 대사나 선택지를 길이만으로 이름표로 분류하지 않습니다. 여러 줄 및 name 키워드로 작성한 고정 Character 정의도 읽으며 게임 코드를 실행하지 않습니다.

이름표에 원문에 없는 인용 대사·줄바꿈·명백한 설명문이 붙으면 해당 항목만 기존 재시도 절차로 처리합니다. 이름 길이의 고정 상한은 두지 않습니다. 정상 항목은 저장하고 두 번 재시도에도 실패한 항목은 원문으로 남깁니다. 저장된 정상/완료 캐시를 새 검사로 전체 재번역하거나 패치 생성을 중단하지 않습니다. 과거 카탈로그에는 저장된 구조 메타데이터에서 용도를 보충하며 원본 게임을 다시 읽거나 캐시를 덮어쓰지 않습니다.

기존 요청 로그에 item_purposes(용도·근거), context_policy(제외한 문맥과 유지한 용어 수)를 추가합니다. validation에는 실패 이유, item_retry에는 개별 재시도, source_fallback에는 원문 유지 사유가 남습니다. 오류 JSON에도 항목 용도와 근거가 포함됩니다. 사용자가 직접 고치는 기존 결과 폴더에는 이 코드 업데이트만으로 변경을 적용하지 않습니다.

Ollama와 진단용 외부 프로그램을 시작할 때 GUI 패키지의 DLL 검색 디렉터리를 분리합니다. 자식 프로세스를 생성하는 동안만 Windows DLL 검색 디렉터리를 초기화하고 즉시 복원하며, 동시 실행은 공통 잠금으로 보호합니다. GUI `_internal`에 속한 PATH 항목도 자식 환경에서 제외합니다. Ollama의 자식 PATH에는 자체 배포본의 C++ DLL 디렉터리를 추가해 시스템에 해당 라이브러리가 없는 포터블 환경에서도 사용할 수 있게 합니다. Windows가 시스템 DLL을 선택할 수도 있으므로 실제 로딩 경로와 버전을 기록합니다. 별도 전역 라이브러리 설치는 필요하지 않습니다. 모델·병렬 처리·KV 캐시·CUDA 연산 설정은 변경하지 않습니다.

기존 서버 로그의 `RPT native launch`와 `data/errors/runtime-recovery.jsonl`의 `server_ready`에는 DLL 분리 정책, 부모 실행 파일, 원래 검색 디렉터리, 제거한 PATH 항목과 서버 작업 디렉터리를 기록합니다. 서버가 실행 중일 때 새 모델 실행 프로세스마다 `runtime_modules`를 기록하며, 실제 DLL 경로·버전과 GUI 패키지 DLL이 섞였는지를 확인합니다. 게임 파일이나 다른 프로그램의 모듈을 조사하지 않습니다.

오류 시 `runtime-<사건 ID>.json`에 분리 정보(`settings._runtime_launch`), 충돌 전 DLL 목록(`module_history`), 오류 시점 DLL 목록(`modules_at_failure`), Windows 충돌 보고 이벤트(`windows_crash_reports`)를 함께 보관합니다. `translation-requests.jsonl`에는 서버 PID와 서버 로그 경로를 추가해 해당 요청과 실행을 연결합니다. DLL 또는 Windows 기록을 읽지 못해도 수집 오류를 남기고 기존 복구를 이어갑니다. 이 수정만으로 GPU 오류의 근본 원인이 해결됐다고 판단하지 않습니다.

HY 번역 기본값은 요청당 16K입니다. 외부 TXT 4,500토큰은 작성 권장량이며 고정 상한이 아닙니다. 필요한 장면은 더 길게 쓸 수 있고, 전체 요청에서 원문·지시·출력 예약을 뺀 공간 안에서 조절합니다. 예전 `context_txt_tokens` 설정으로 잘라내지 않습니다. context가 없으면 기존 방식으로 진행합니다. 현재 모델을 HY로 강제 변경하지 않습니다.

원본 게임의 `game/context`에서 공통·용어·해당 대본 파일을 읽습니다. 원본이 이동됐거나 독립 repair 실행이면 준비된 staging의 문맥을 사용합니다. `characters.txt`는 관리용이며 자동으로 전체 주입하지 않습니다. 파일 형식은 `grok-context-preparation.txt`를 참고하세요.

현재 상태는 Scene ID / State ID와 Applies to의 원문 앵커·실제 label·Start ID/End ID로 선택합니다. 상태 경계에서는 배치를 나눕니다. 서로 겹치거나 모호한 범위, 실행 시점에만 알 수 있는 Branch/Condition은 추측하지 않고 공통·용어만 사용하며 경고를 남깁니다. 일반적인 분기 실행기를 구현한 것은 아닙니다.

짧은 앵커도 원문 대사 전체와 정확히 일치하면 사용합니다. label의 백틱 표기와 labels 목록을 읽고, Applies to에 라벨이 없으면 Management의 명시적인 labels 필드로 검색 범위를 좁힙니다. 관리용 설명 자체는 주입하지 않습니다. 같은 끝 대사가 다른 라벨에도 나오면 시작 라벨 안의 유일한 후보를 우선하며, 같은 범위 안에서 여전히 중복되면 그 이유와 후보 수를 기록합니다. 지정 라벨에 카탈로그 항목이 없으면 `no_catalog_entries`로 구분합니다.

첫 Scene ID 앞의 File overview에 있는 Injection context도 `translation_guidance.file`로 전달합니다. 파일 배경은 현재 장면보다 우선하지 않으며 이후 관계 변화를 앞당겨 적용하지 않도록 지시합니다. `말투 A→B:`, `Register A→B:` 같은 방향별 필드도 현재 말투로 추출합니다.

화자·청자·현재 관계·말투의 명시적인 한 줄 필드는 번역 대상 가까이에도 배치합니다. 별도 AI 분석을 하지 않습니다. 이 배치의 번역 품질 향상은 보장하지 않습니다. 이름 변수는 기존 기본 이름·분류 메타데이터와 연결하며, TXT의 용어를 자동 인명 목록에 추가하지 않습니다.

요청 전 도구 소유 Ollama 모델을 빈 프롬프트로 적재하고 같은 런타임의 토크나이저로 최종 입력을 계산합니다. 토크나이저를 사용할 수 없으면 보수적 추정임을 경고·기록합니다. 번역 대기열에서는 창을 넘는 배치를 먼저 나눕니다. 이 분할에는 번역 모델 호출이나 실패 재시도 횟수를 사용하지 않습니다.

앞뒤 원문은 남는 공간에 맞춰 대사 항목 전체를 넣습니다. 기존 1,200 추정 토큰·24개 제한은 사용하지 않습니다. label·분기·이동·TXT 장면/상태 경계를 넘지 않고, 긴 항목을 건너뛴 뒤 먼 대사를 붙이지 않습니다. 이미지 교체인 `scene` 명령만으로 대화를 끊지는 않습니다. 번역 대상 사이의 이미 번역된 대사도 보존합니다. 원문 자체가 여러 항목으로 나뉘어 있으면 가까운 항목과 대상 위치를 함께 전달하되, 게임의 항목을 합치지는 않습니다.

한 항목으로 나눠도 공간이 부족하면 먼 주변 대사를 통째로 제외하고, TXT의 공통·장면·용어 자료를 완전한 줄/용어 단위로 줄입니다. 가장 가까운 앞뒤 대사는 이 단계까지 유지하며, 그 후에도 부족할 때만 통째로 제외합니다. 현재 관계·말투 필드는 마지막까지 우선합니다. 번역 대상 자체는 자르지 않습니다. 대상만으로 창을 넘으면 해당 항목과 예산을 오류로 남깁니다. 완전한 문맥을 전달해도 모델의 오역 자체를 보장해서 막을 수는 없습니다.

도구 소유 런타임은 RAM prompt cache를 비활성화하고 Q8 KV / Flash Attention을 사용합니다. API에서 보고한 모델·컨텍스트·GPU 할당 값과 서버 로그 위치를 기록합니다. GPU 메모리 할당 보고는 물리적 상주 메모리 전체를 보장하는 수치가 아닙니다.

프로젝트 내부 `data`의 로그:

- `context-report.json`: 읽은 TXT, 파일 해시, 구간 매칭 문제. `scope_details`에 구간별 라벨·후보 수·시작/끝 앵커의 일치 수·연결된 ID/행·중복 수·실패 이유를 기록합니다.
- `context-history.jsonl`: 실행별 문맥 로딩 기록.
- `translation-requests.jsonl`: 요청 ID별 실제 프롬프트·응답, 적용 구간·파일 해시, 토큰 계산 방식과 예산, 제외한 방향·첫 항목 ID 또는 제외 단위 수·해시, API가 보고한 입력 토큰. 배치 분할은 `budget_split`으로 기록합니다. TXT를 전부 제외한 경우에도 파일·범위·제외 이유를 남깁니다.
- `errors/*.json`: 발생 단계·관련 파일/항목 ID·설정·예외·traceback·항목별 검증 실패 이유·재개 안내. 콘솔과 GUI 작업 로그에도 출력됩니다.
- 프로젝트가 정해지기 전의 오류는 프로그램 `logs/errors`에 저장됩니다.

기존 성공 번역은 8K→16K 설정 변경 또는 TXT 수정만으로 삭제·재번역하지 않습니다. 일반 번역 재개는 저장된 항목을 재사용합니다. 새 문맥으로 비교하려면 재번역을 선택하세요. 새 항목에는 사용한 문맥 해시와 요청 ID를 저장합니다. 과거 항목의 문맥 정보는 소급해서 만들어 넣지 않습니다.

번역 중 모델 서버의 HTTP 500/502/503/504, 연결 끊김 또는 시간 초과가 발생하면 이미 완료된 배치를 저장하고 도구가 실행한 서버를 종료한 뒤 같은 설정으로 재시작합니다. 저장되지 않은 항목만 다시 요청하며, 동시 요청이 함께 실패해도 재시작은 한 곳에서만 처리합니다. 이전 서버 종료 실패·남아 있는 요청 스레드·사용자 취소 시에는 재시작하지 않습니다. 한 번의 번역 실행에서 자동 재시작은 최대 2회입니다. 출력 검증 실패는 기존 항목별 재시도를 사용합니다.

오류 자료는 `data/errors/runtime-<사건 ID>.json`, `.server.log`와 `runtime-recovery.jsonl`에 남습니다. HTTP 오류 본문, 요청 로그 연결, 모델·실행 옵션, 서버 시작 및 마지막 로그, 최근 GPU/시스템 메모리 추이, 서버 프로세스 메모리, 오류 시각 주변 Windows GPU/응용 프로그램 기록, 저장·재시작 결과를 포함합니다. 자원 추이는 최근 150개 샘플을 메모리에 보관하다 오류 시 저장합니다. 수집 불가 항목도 이유를 기록하며 진단 수집 실패만으로 복구를 막지 않습니다. 평상시 CUDA 동기 진단을 강제하거나 모델·문맥·캐시 설정을 자동 변경하지 않습니다. 자동 복구는 CUDA 근본 원인을 해결했다는 뜻이 아닙니다.
